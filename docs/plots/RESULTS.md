# Results: Dense vs Sparse Conjugate Gradient on TACC Vista

This page tracks how the CPU solver evolved, what each version measured, and the
performance issues still open before moving to the GPU.

**Problem.** Solve `A x = b` (with `b = 1`) by Conjugate Gradient (CG), stopping at
relative residual < 1e-5, where `A` is a sparse symmetric positive definite (SPD)
matrix from a finite-element / finite-difference discretization.

**Machine.** TACC Vista `gg` node: 2 × NVIDIA Grace CPU (Arm Neoverse V2), 144 cores
total (72 per socket), one NUMA node per socket. GCC `-O3 -mcpu=native -fopenmp`,
threads pinned with `OMP_PLACES=cores OMP_PROC_BIND=close`.

**Test matrices.** 2D Poisson (5-point Laplacian) on an n × n grid: N = n² unknowns,
about 5 nonzeros per row, always SPD. Generated by `gen_poisson.py` for n = 30 … 2000
(N = 900 … 4,000,000), so the size can be swept in a controlled way.

**Method.** Every (program, matrix, thread count) is run 3 times; plots use the median
solve time. Solve time excludes reading the file and building the matrix.
Run with `sbatch benchmark.sh`; plots by `plot_compare.py`.

## 1. Progression

| Version | Program | Storage | Work per CG iteration | Status |
|---|---|---|---|---|
| v0 | serial dense CG | N × N array | O(N²) | baseline |
| v1 | `cpu_only` | N × N array, OpenMP | O(N²) / threads | done |
| v2 | `cpu_sparse` | CSR + RCM reordering, OpenMP | O(nnz) / threads | done |
| v3 | `cpu_sparse` + fixes (§4) | CSR, NUMA- and sync-tuned | O(nnz) / threads | next |
| v4 | GPU (cuSPARSE) | CSR on the GPU | O(nnz), GPU bandwidth | planned |

### v0 → v1: multithreading the dense solver
The dense solver keeps the whole loop in one OpenMP parallel region with three fused
passes per iteration. It scales well on small matrices because each iteration does N²
multiply-adds, which gives every thread a large share of work:

| Matrix | N | 1 thread | 144 threads | Speedup |
|---|---|---|---|---|
| poisson2d_90 | 8,100 | 3,115 ms | 55 ms | **57×** |

But the work and memory are still N². A real SuiteSparse matrix, `barth` (N = 6,691),
took **137.6 s** on one Vista core, and a 2000 × 2000 grid would need
**128,000 GB** for the dense array, about 500× the memory of the node.

### v1 → v2: sparse storage (CSR)
`cpu_sparse` follows the pipeline in `cpu_high_level.txt`: read into COO, check the
sparsity, reorder with Reverse Cuthill-McKee, convert to CSR (nonzeros only), then run
the same fused CG with a sparse matrix-vector product.

It gives the **same iterations and residual** as the dense version on every matrix
(its solution for `poisson2d_30` is identical to the dense one), and it is much faster:

| Matrix | N | Dense, 1 thread | Sparse, 1 thread | Sparse is faster by |
|---|---|---|---|---|
| poisson2d_30 | 900 | 12.7 ms | 0.15 ms | ~80× |
| poisson2d_60 | 3,600 | 489 ms | 1.35 ms | ~360× |
| poisson2d_90 | 8,100 | 3,115 ms | 4.4 ms | ~700× |
| poisson2d_2000 | 4,000,000 | cannot run (128,000 GB) | 60.6 s | — |

On the 2000 grid, sparse needs about 240 MB for the matrix. One thread does
3,073 iterations at about 20 ms each, which is about **35 GB/s** of memory traffic
(≈ 690 MB per iteration), roughly what one core can pull from memory.

  matrices peak early and then slow down. §3 explains why.

## 3. Performance issues found

### 3.1 CG is memory-bandwidth bound, so "ideal" speedup is not reachable
Each iteration streams the whole matrix and about 13 vector passes through memory and
does only ~2 floating-point operations per 12 bytes of matrix. Speed is set by memory
bandwidth, not core count. One core already uses about 35 GB/s, and the memory system
of a socket can supply only a limited multiple of that, so even perfect code reaches
roughly 15–30× per socket, not 72×. The sparse curves flattening is mostly this
ceiling. **The GPU's much higher memory bandwidth is the main reason for v4.**

*Verify:* `perf stat -e cycles,instructions,stall_backend,ll_cache_miss_rd` at 1, 16, 64
and 144 threads. Expect low IPC (< 1) with backend stalls dominating. Compare the
achieved GB/s against a STREAM triad run on the same node.

### 3.2 Thread placement uses only one socket up to 72 threads
With `OMP_PROC_BIND=close`, threads 1–72 all run on socket 0, so up to 64 threads the
program uses half the node's memory bandwidth. This matches the jump on the 2000 grid
from about 17× at 64 threads to about 43× at 128 threads, when the second socket joins.

*Verify:* rerun with `OMP_PROC_BIND=spread`, which uses both sockets from the start.
*Fix:* use `spread` for large, memory-bound matrices.

### 3.3 Synchronization overhead dominates small matrices
Every CG iteration has five points where all threads wait: three reductions
(`p·Ap`, `r·z`, `r·r`), one `single`, and one barrier. Across two sockets with 144
threads each one costs microseconds. When an iteration's real work is small, this
overhead takes over:

| poisson2d_90 (sparse) | 1 thread | 4 threads | 16 | 64 | 144 |
|---|---|---|---|---|---|
| Solve time | 4.4 ms | **1.96 ms** | 2.3 ms | 7.3 ms | 44.8 ms |

This is why the 120–1000 grids peak at 4–64 threads and then slow down.

*Verify:* `perf record` at 144 threads and check the share of samples in `libgomp`
barrier and wait functions (`gomp_team_barrier_wait`, `do_spin`).
*Fix:* choose the thread count from the problem size; merge the reductions (pipelined
CG) to cut synchronization points per iteration from 5 to 2.

### 3.4 Incomplete NUMA first-touch
The matrix values, column indices and work vectors are first written in parallel with
the same row split the solver uses, so their memory sits near the threads that use it.
But `x`, `b` and the CSR row pointers are initialized by one thread, so all of their
memory lives on socket 0, and threads on socket 1 read and write `x` across the
socket link every iteration. This likely contributes to the drop from 128 to 144
threads on the 2000 grid.

*Verify:* `numastat -p <pid>` during a 144-thread run.
*Fix:* initialize `x`, `b` and the row pointers in parallel with the solver's partition.

### 3.5 Reduction variables share a cache line (true sharing)
The reduction targets (`pAp`, `rz_new`, `rr`, `b_norm2`) are adjacent variables on
one 64-byte cache line. At the end of each reduction loop all threads combine into
them, so that line moves between cores every iteration. Classic false sharing in
the vector updates is unlikely: each thread writes a contiguous block of thousands of
cache lines and shares at most one line with its neighbor.

*Verify:* `perf c2c` (needs Arm SPE support, which may not be enabled on Vista); if it
is unavailable, pad each variable to its own 64-byte line and re-measure.
*Fix:* `alignas(64)` per reduction variable, or per-thread partial sums combined once.

### 3.6 Test matrices: most cannot be solved by CG
24 of the 25 matrices on the `test_matrices` branch are unsymmetric, so CG never
converges on them (`barth`, for example, stopped at 5,000 iterations with residual
0.60), and `young1c` is complex-valued. The size sweep therefore uses Poisson grids.
*Next:* add real SPD matrices from SuiteSparse (filter: real, positive definite), for
example `bcsstk17`, `Pres_Poisson`, `thermal1`, `apache1`.

### 3.7 Benchmark issues found and fixed
- **Runs used 1 core.** TACC sets `OMP_NUM_THREADS=1` in batch jobs, and `nproc`
  obeys it, so the scripts saw 1 core. Fixed with
  `NCORES=$(env -u OMP_NUM_THREADS -u OMP_THREAD_LIMIT nproc)` and `#SBATCH -c 144`.
- **Relative `TEST_DIR` broke** because the script changes into its work folder;
  the path is now converted to an absolute one.
- **Duplicate matrices** (`.mtx` and `.mtx.gz` copies of the same file) doubled run
  time; benchmark one folder at a time.
